# Template Mass Update — Overwrite Old Template + debug cleanup (2026-10-05)

## Summary
Added an **Overwrite Old Template** option to the Template Mass Update feature and
removed the temporary debug instrumentation left over from the merge-field
matching fixes. Overwrite lets admins replace each matched template **in place**
(same template ID, same filename, no dated-suffix copy), which is required for the
800+ template email update where stakeholders do not want template titles to change.

## Changes

### Backend — `backend/routes/template_update.py`
- `_Options` gained an `overwrite: bool` flag.
- `_build_options(...)` now accepts an `overwrite` form value (parsed via `_as_bool`,
  default `False`).
- `execute_template_update(...)` added an `overwrite` form field (`default="false"`).
  Remains admin-only (`require_admin`) and background-job based.
- `_run_template_job(...)` upload step now branches:
  - **overwrite = false (default, non-destructive):** `upload_template(..., mode="create")`
    with the dated-suffix filename — original untouched. (unchanged behavior)
  - **overwrite = true (destructive, in place):** first tries `upload_template(...,
    template_id=tid, mode="update")` — a PATCH that keeps the original filename.
    **If the PATCH fails** (`ClioAPIError`, e.g. the account rejects a file-bearing
    PATCH), it falls back to the legacy create+delete contract: create a NEW
    template with the same name, then `delete_template(tid)` the old one. The result
    row records `overwrite_method` ("patch" or "create_delete"), `old_deleted`, and
    any `delete_error` / `patch_fallback_reason`.
  - Result rows carry `overwritten` plus the resulting template id/filename.
  - Audit rows record overwrite vs. create (and the overwrite method) in
    `after_value` / `details`.
  - Post-upload verification (`verify_docx_bytes`) runs in both modes.

### Backend — `clio_client.py`
- Added `delete_template(template_id)`: a DELETE that tolerates 204/empty bodies
  (the generic `delete()` JSON-decodes and would fail), reuses token-refresh /
  429 / 5xx handling, treats 2xx and 404 as success, and tries both URL shapes
  (`document_templates/{id}.json` and `document_templates/{id}`) like the legacy app.
- Job completion message reflects the mode: "Overwrote N template(s)" vs.
  "Created updated copies for N template(s)" vs. "Previewed ...".

### Frontend — `frontend/src/pages/TemplateMassUpdatePage.jsx`
- New `overwrite` state.
- `buildForm()` now sends `overwrite`; the `filename_suffix` is only sent when
  overwrite is off (it is irrelevant for in-place updates).
- Added a **sliding toggle "Overwrite Old Template"**, placed between the
  Preview/Download-report button row and the filename-suffix warning line (top of
  the admin Execute block).
- When overwrite is ON: the amber "creates a NEW template" notice is swapped for a
  rose/destructive notice, the filename-suffix input is disabled (with a hint), and
  the confirmation checkbox label switches to an explicit OVERWRITE confirmation.

### Cleanup — `backend/services/docx_replace.py`
- Removed all temporary Debug Mode instrumentation (`# #region agent log` blocks
  writing to `debug-855657.log`) from `_replace_in_text_chunks` and
  `_process_paragraph`. The merge-field double-replacement and partial-match fixes
  are unchanged and remain verified.
- Deleted the `debug-855657.log` output file.

## Why
Stakeholders do not want template titles to change or carry an `updated_mmddyyyy`
suffix. In-place overwrite (PATCH) satisfies that while preserving the audit trail
and post-upload verification. The legacy standalone app used the same PATCH
`document_templates/{id}.json` contract (`clio_client.upload_template` already
exposed `mode="update"`), so no new Clio client plumbing was needed.

## How it achieves the intent
- Overwrite path keeps the original template ID and filename, so links and names in
  Clio stay stable; the file content is replaced with the rewritten bytes.
- Boundary-aware merge-field matching (prior fix) ensures only exact merge fields
  are changed, so overwriting in place is safe against partial/substring matches.
- The destructive mode is gated behind admin auth, an explicit toggle, and a
  confirmation checkbox, and still runs as a cancelable background job.

## Validation

- Backend modules compile (`py_compile`).

# Billing Dashboard — refresh window fix, debug cleanup, donut charts (2026-10-05, later)

## Summary
Three related changes to the Billing & Activities Dashboard:
1. Manual refresh default window reduced from 190 to 35 days so a sync finishes
   in minutes instead of ~35-40 min (root cause of the perpetually stale
   "Last Refreshed" data — confirmed fixed in Prod, ~8 min to fresh data).
2. Removed all temporary `[debug-855657]` instrumentation added during the
   reliability investigation.
3. Converted the "Top Time Categories" and "Top Expense Categories" widgets
   from horizontal bar lists to donut charts per the approved mockup.

## Changes

### Backend — `backend/routes/billing.py`
- `refresh_activities` POST endpoint: `reconcile_days` default changed from
  `_FULL_RECONCILE_DAYS` (190) to `_RECONCILE_DAYS_DEFAULT` (35). A 190-day
  full reconcile is still available by passing `reconcile_days` explicitly.
- Removed debug instrumentation (`_dbg` helper and all H5/H6/H7 log blocks in
  `_run_refresh_job`, `_refresh_cache`, `_stream_upsert`).

### Backend — `backend/main.py`
- Removed debug instrumentation: `_dbg` helper, the H4 `init_db()` wrapper
  (restored to a plain call), the H2 per-request logging middleware, and the
  H1 frontend-mount check.

### Frontend — `frontend/src/pages/BillingDashboardPage.jsx`
- New `TIME_DONUT_COLORS` and `EXPENSE_DONUT_COLORS` constants near the top of
  the file (clearly commented "EDIT HERE") — each is a 10-entry hex palette,
  one color per category rank, driving both the donut slices and the tooltip
  swatches. Edit these arrays to re-theme per stakeholder preference.
- New `CategoryDonut` component (Chart.js `doughnut` via canvas refs, same
  pattern as `MonthlyBarChart`): donut aligned left; right side lists
  "CategoryName: $figure" (e.g., `Draft/Revise: $1,500,000.00`).
- Slice hover tooltip: abbreviated Timeframe date span as the title
  (smaller font, upper-left, e.g., `Sept 1st '26 - Sept 30th '26`, tracking
  the default or user-filtered window via `summary.card_date_from/to`), then
  a colored box matching the slice with `Category: $figure` beside it.
- New helpers `formatShortRangeDate` / `ordinalDay` for the abbreviated span.
- Replaced the old `CategoryList` horizontal-bar component with `CategoryDonut`
  in both Top Category tiles; still renders the same Top 10 data from
  `by_category_time` / `by_category_expense`.
- Rebuilt `frontend/dist` (`npm run build`).

## Verification
- `py -3 -m py_compile backend/main.py backend/routes/billing.py` — OK.
- `npm run build` — OK (4.3s).
- Refresh-window fix verified in Prod by user (dashboard updated ~8 min).
